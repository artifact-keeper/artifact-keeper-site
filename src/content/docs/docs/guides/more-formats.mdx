Artifact Keeper supports a wide variety of specialized package formats beyond traditional software dependencies. This guide covers ML/AI models, editor extensions, Git LFS, and generic file storage.

## ML / AI

### HuggingFace

Host private machine learning models using the HuggingFace Hub protocol.

**Endpoint Format:** `/huggingface/{repo}`
**Repository Key:** `huggingface`
**Supported Clients:** `huggingface_hub`, `transformers`

#### Python SDK Configuration

Install the HuggingFace Hub library:

```bash
pip install huggingface_hub
```

Configure authentication:

```python
from huggingface_hub import login

# Login with token
login(token="your_artifact_keeper_token")
```

Or set environment variable:

```bash
export HUGGING_FACE_HUB_TOKEN=your_artifact_keeper_token
export HF_ENDPOINT=https://artifacts.example.com/huggingface/main
```

#### Uploading Models

Upload a model to Artifact Keeper:

```python
from huggingface_hub import HfApi

api = HfApi(endpoint="https://artifacts.example.com/huggingface/main")

# Upload entire model directory
api.upload_folder(
    folder_path="./my-model",
    repo_id="myorg/my-model",
    repo_type="model",
)

# Upload single file
api.upload_file(
    path_or_fileobj="./model.safetensors",
    path_in_repo="model.safetensors",
    repo_id="myorg/my-model",
)
```

#### Downloading Models

Download models from your private repository:

```python
from huggingface_hub import hf_hub_download
from transformers import AutoModel

# Download specific file
model_path = hf_hub_download(
    repo_id="myorg/my-model",
    filename="model.safetensors",
    endpoint="https://artifacts.example.com/huggingface/main",
)

# Load model with transformers
model = AutoModel.from_pretrained(
    "myorg/my-model",
    endpoint="https://artifacts.example.com/huggingface/main",
)
```

#### Snapshots and Revisions

Work with specific model versions:

```python
from huggingface_hub import snapshot_download

# Download entire model snapshot
snapshot_download(
    repo_id="myorg/my-model",
    revision="v1.0.0",
    endpoint="https://artifacts.example.com/huggingface/main",
)
```

#### Remote Repositories and Xet Storage

When a HuggingFace repository is configured as **remote** (pull-through to
`https://huggingface.co`), disabling Xet on the client is recommended:

```bash
export HF_HUB_DISABLE_XET=1
export HF_ENDPOINT=https://artifacts.example.com/huggingface/hf-remote

hf download openai-community/gpt2
```

:::caution
Without `HF_HUB_DISABLE_XET=1`, `hf download` fails with a `404` on
`/api/models/{model_id}/xet-read-token/{revision}`.

The Hub now serves most models through Xet, its content-addressed storage
backend. `huggingface_hub` detects Xet-backed files from the upstream file
listing and then requests a Xet access token, which Artifact Keeper does not
issue. Setting the variable makes the client use the ordinary `/resolve/`
download path, which is fully supported.
:::

Disabling Xet does not change what you get: the downloaded files are
byte-identical, and integrity is still verified against the upstream checksum.
Only the transfer mechanism differs — plain HTTP range downloads instead of
Xet's chunked deduplication.

This applies to remote (proxying) repositories only. Hosted repositories that
you upload models to yourself are unaffected, since their files never come from
the Hub.

### ML Model (Generic)

For models not using HuggingFace format, use the generic ML model endpoint.

**Endpoint Format:** `/mlmodel/{repo}`
**Repository Key:** `mlmodel`

:::tip
Enable [artifact versioning](/docs/advanced/versioning) on an `mlmodel` repository to keep an immutable revision history of each model path — re-uploads append a new revision instead of overwriting, so you can retrieve and roll back to any prior version.
:::

Upload models via HTTP API:

```bash
# Upload model file
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@model.onnx" \
  -F "metadata={\"framework\":\"onnx\",\"version\":\"1.0.0\"}" \
  https://artifacts.example.com/mlmodel/main/models/my-model/1.0.0

# Download model
curl -H "Authorization: Bearer $TOKEN" \
  https://artifacts.example.com/mlmodel/main/models/my-model/1.0.0/model.onnx \
  -o model.onnx
```

Python example:

```python
import requests

# Upload
with open("model.onnx", "rb") as f:
    response = requests.post(
        "https://artifacts.example.com/mlmodel/main/models/my-model/1.0.0",
        headers={"Authorization": f"Bearer {token}"},
        files={"file": f},
        data={"metadata": '{"framework":"onnx","version":"1.0.0"}'},
    )

# Download
response = requests.get(
    "https://artifacts.example.com/mlmodel/main/models/my-model/1.0.0/model.onnx",
    headers={"Authorization": f"Bearer {token}"},
)
with open("model.onnx", "wb") as f:
    f.write(response.content)
```

## Editor Extensions

### VS Code Extensions

Host private VS Code extensions (also compatible with Cursor, Windsurf, and Kiro).

**Endpoint Format:** `/vscode/{repo}`
**Repository Key:** `vscode`
**Aliases:** `cursor`, `windsurf`, `kiro`

#### Private Marketplace Configuration

Configure VS Code-compatible editors that support custom galleries by editing
their `product.json` extension gallery settings. VS Code itself does not expose
a supported `settings.json` key for replacing the Microsoft Marketplace.

```json
{
  "extensionsGallery": {
    "serviceUrl": "https://artifacts.example.com/vscode/main",
    "itemUrl": "https://artifacts.example.com/vscode/main/item",
    "resourceUrlTemplate": "https://artifacts.example.com/vscode/main/{publisher}/{name}/{version}",
    "extensionUrlTemplate": "https://artifacts.example.com/vscode/main/{publisher}/{name}/latest"
  }
}
```

For VSCodium, edit `product.json` as documented in its custom extension gallery
guide. For editors that do not support `product.json` edits, use a gallery
manager such as VSIX Manager or install the downloaded `.vsix` files directly.

#### Publishing Extensions

Package and publish your extension:

```bash
# Install vsce
npm install -g @vscode/vsce

# Package extension
vsce package

# Publish to Artifact Keeper
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@my-extension-1.0.0.vsix" \
  https://artifacts.example.com/vscode/main/extensions
```

#### Installing Private Extensions

Install extensions from your private marketplace:

```bash
# Via command line
code --install-extension myorg.my-extension

# Or search in Extensions view (if marketplace is configured)
```

### JetBrains Plugins

Host private IntelliJ IDEA, PyCharm, WebStorm, and other JetBrains IDE plugins.

**Endpoint Format:** `/jetbrains/{repo}`
**Repository Key:** `jetbrains`

#### Custom Plugin Repository Configuration

Add your custom repository in JetBrains IDE:

1. Open Settings/Preferences
2. Go to Plugins
3. Click the gear icon → Manage Plugin Repositories
4. Add: `https://artifacts.example.com/jetbrains/main/updatePlugins.xml`

Or configure via `idea.properties`:

```properties
idea.plugins.host=https://artifacts.example.com/jetbrains/main
```

#### Publishing Plugins

Build and publish your plugin:

```bash
# Build plugin
./gradlew buildPlugin

# Upload to Artifact Keeper
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@build/distributions/my-plugin-1.0.0.zip" \
  https://artifacts.example.com/jetbrains/main/plugins
```

Or use Gradle plugin:

```kotlin
// build.gradle.kts
publishPlugin {
    host.set("https://artifacts.example.com/jetbrains/main")
    token.set(System.getenv("ARTIFACT_KEEPER_TOKEN"))
}
```

```bash
./gradlew publishPlugin
```

### JupyterLab Extensions

Host JupyterLab extensions through the PyPI, npm, and conda repositories you
already have. Prebuilt extensions are pip wheels, source extensions are npm
packages, and classic notebook extensions (nbextensions) ship as either or as
conda packages.

**Endpoint Format:** `/pypi/{repo}`
**Repository Key:** `jupyter` (alias of `pypi`, Artifact Keeper 1.10.0+) — or any existing `pypi`, `npm`, or `conda_native` repository

**Prebuilt extensions:** any PyPI repository

```bash
pip install --index-url https://artifacts.example.com/pypi/main/simple/ jupyterlab-git
```

**Source extensions:** any npm repository. JupyterLab 4 rebuilds itself with
its bundled Yarn 3, which does not read `.npmrc`; set the registry for the
build instead:

```bash
export YARN_NPM_REGISTRY_SERVER=https://artifacts.example.com/npm/main/
jupyter labextension install @myorg/my-extension   # deprecated in JupyterLab 4, requires Node.js
```

Prefer publishing extensions as prebuilt wheels to a PyPI repository; the
`.npmrc` `registry=` line only affects `npm`/`yarn` 1 clients that fetch the
package directly.

**Classic nbextensions:** the same PyPI or npm repository, or a conda repository

```bash
conda install -c https://artifacts.example.com/conda/main jupyter_contrib_nbextensions
```

See the [PyPI](/docs/guides/pypi), [npm](/docs/guides/npm), and
[Conda](/docs/guides/more-languages#conda) guides for authentication and
remote/virtual setup.

#### Extension Manager Sidebar

JupyterLab 4's Extension Manager talks to two PyPI APIs beyond the Simple index:
the legacy JSON API (`/pypi/{name}/json`) for metadata and XML-RPC `browse` for
discovery. Artifact Keeper serves both on the PyPI handler, so one line in
`jupyter_lab_config.py` points the sidebar at your repository:

```python
c.PyPIExtensionManager.base_url = "https://artifacts.example.com/pypi/main/pypi"
```

Installs started from the sidebar run `pip`, so keep pip's `index-url` pointed
at the same repository:

```ini
# pip.conf
[global]
index-url = https://artifacts.example.com/pypi/main/simple/
```

:::note
The Extension Manager sidebar requires **Artifact Keeper 1.10.0 or later**,
which adds the legacy PyPI JSON API and XML-RPC `browse` to the PyPI handler
([artifact-keeper#3783](https://github.com/artifact-keeper/artifact-keeper/issues/3783)).
The `jupyter` repository key also arrives in 1.10.0
([artifact-keeper#3784](https://github.com/artifact-keeper/artifact-keeper/issues/3784));
on earlier versions, use a `pypi` repository. `pip`, `npm`, and `conda`
installs work on any version.
:::

Hosted repositories answer `browse` from stored package metadata (the
`Framework :: Jupyter :: JupyterLab :: Extensions :: Prebuilt` classifier); a
virtual repository answers with the union of its hosted members — remote
members contribute nothing to the catalogue. Only uploads made on 1.10.0 or
later store classifiers; re-upload older wheels to list them in the sidebar.

Remote repositories do not answer `browse` at all: the call returns an XML-RPC
fault (`-32001`) rather than being forwarded to the upstream, and JupyterLab
shows it as a generic "Error searching for extensions". The reason is in the
XML-RPC response and the server log. Point `base_url` at a hosted repository,
or at a virtual repository that has at least one hosted member; installs from a
remote still work through `pip`, only the sidebar catalogue does not.

The JSON views the sidebar reads apply the same listing-time gates as
`/simple/`: [curation](/docs/security/curation/) block rules, the
[age gate](/docs/security/age-gate/) on a remote member, and PEP 708 local-first
isolation on a virtual repository, so the sidebar never offers a version whose
download would be refused. Installs run `pip`, so [quarantine and scan
policies](/docs/security/scanning/) apply to the download exactly as for any
other `pip install`.

## Git LFS

Store large files using Git Large File Storage protocol.

**Endpoint Format:** `/lfs/{repo}`
**Repository Key:** `gitlfs`

### .lfsconfig Setup

Configure Git LFS to use Artifact Keeper:

```ini
# .lfsconfig (committed to repository)
[lfs]
    url = https://artifacts.example.com/lfs/main
```

Or configure globally:

```bash
git config --global lfs.url https://artifacts.example.com/lfs/main
```

### Git LFS Configuration

Install and configure Git LFS:

```bash
# Install Git LFS
git lfs install

# Set credentials
git config lfs.https://artifacts.example.com/lfs/main.access token
# Enter your Artifact Keeper token when prompted
```

Or use credential helper:

```bash
git config --global credential.helper store
echo "https://username:token@artifacts.example.com" >> ~/.git-credentials
```

### Tracking and Pushing Large Files

Track file patterns with Git LFS:

```bash
# Track large file types
git lfs track "*.psd"
git lfs track "*.zip"
git lfs track "*.bin"
git lfs track "models/*.h5"

# Verify tracked patterns
git lfs track

# Commit .gitattributes
git add .gitattributes
git commit -m "Configure Git LFS tracking"
```

Add and push large files:

```bash
# Add large file
git add large-file.bin

# Commit
git commit -m "Add large binary file"

# Push (LFS files uploaded automatically)
git push origin main
```

### Cloning Repositories with LFS

Clone repositories with large files:

```bash
# Clone with LFS files
git clone https://github.com/myorg/myrepo.git

# Clone without downloading LFS files initially
GIT_LFS_SKIP_SMUDGE=1 git clone https://github.com/myorg/myrepo.git

# Pull LFS files later
git lfs pull
```

### Managing LFS Files

```bash
# List LFS files
git lfs ls-files

# Fetch specific files
git lfs fetch --include="*.psd"

# Prune old LFS files
git lfs prune
```

## Eclipse P2

Host Eclipse IDE plugins and update sites.

**Endpoint Format:** `/p2/{repo}`
**Repository Key:** `p2`

### Eclipse IDE Update Site Configuration

Add your P2 repository in Eclipse:

1. Help → Install New Software
2. Click "Add..."
3. Enter:
   - Name: `My Private Plugins`
   - Location: `https://artifacts.example.com/p2/main`

Or configure via `p2.inf`:

```ini
# p2.inf
instructions.configure=\
  addRepository(type:0,location:https${#58}//artifacts.example.com/p2/main);\
  addRepository(type:1,location:https${#58}//artifacts.example.com/p2/main);
```

### Publishing P2 Content

Upload update site content:

```bash
# Build P2 repository with Tycho
mvn clean package

# Upload content
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@target/repository/content.xml" \
  https://artifacts.example.com/p2/main/

curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@target/repository/artifacts.xml" \
  https://artifacts.example.com/p2/main/
```

## Generic

Store any file type with custom metadata using the generic storage endpoint.

**Endpoint Format:** `/generic/{repo}`
**Repository Key:** `generic`

:::tip
Enable [artifact versioning](/docs/advanced/versioning) on a `generic` repository to append an immutable revision on every re-upload to a path (instead of overwriting), with a `?version=<rev|label>` selector for retrieving any prior revision.
:::

### Upload Examples

Upload files via curl:

```bash
# Upload single file
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@build-output.tar.gz" \
  https://artifacts.example.com/generic/main/builds/v1.0.0/output.tar.gz

# Upload with custom metadata
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@docs.zip" \
  -F "metadata={\"type\":\"documentation\",\"version\":\"1.0.0\",\"commit\":\"abc123\"}" \
  https://artifacts.example.com/generic/main/docs/v1.0.0/docs.zip
```

Python example:

```python
import requests

# Upload file
with open("artifact.bin", "rb") as f:
    response = requests.post(
        "https://artifacts.example.com/generic/main/artifacts/v1.0.0/artifact.bin",
        headers={"Authorization": f"Bearer {token}"},
        files={"file": f},
        data={
            "metadata": json.dumps({
                "build_id": "12345",
                "platform": "linux-x64",
                "checksum": "sha256:abc123...",
            })
        },
    )

print(response.json())
```

### Download Examples

Download files via curl:

```bash
# Download file
curl -H "Authorization: Bearer $TOKEN" \
  https://artifacts.example.com/generic/main/builds/v1.0.0/output.tar.gz \
  -o output.tar.gz

# Download with metadata
curl -H "Authorization: Bearer $TOKEN" \
  https://artifacts.example.com/generic/main/builds/v1.0.0/output.tar.gz?metadata=true
```

Python example:

```python
import requests

# Download file
response = requests.get(
    "https://artifacts.example.com/generic/main/artifacts/v1.0.0/artifact.bin",
    headers={"Authorization": f"Bearer {token}"},
)

with open("artifact.bin", "wb") as f:
    f.write(response.content)

# Get metadata
response = requests.get(
    "https://artifacts.example.com/generic/main/artifacts/v1.0.0/artifact.bin",
    headers={"Authorization": f"Bearer {token}"},
    params={"metadata": "true"},
)

metadata = response.json()
print(f"Build ID: {metadata['build_id']}")
```

### Use Cases

**Build Outputs:**
```bash
# Store compiled binaries
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@app-linux-x64" \
  https://artifacts.example.com/generic/main/releases/v1.0.0/linux/app

# Store build artifacts
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@build-artifacts.zip" \
  https://artifacts.example.com/generic/main/builds/${BUILD_ID}/artifacts.zip
```

**Documentation Bundles:**
```bash
# Upload generated docs
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@docs-bundle.tar.gz" \
  https://artifacts.example.com/generic/main/docs/v1.0.0/bundle.tar.gz
```

**Proprietary Formats:**
```bash
# Store custom file formats
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@project.proprietary" \
  -F "metadata={\"type\":\"project\",\"tool\":\"CustomTool\",\"version\":\"3.0\"}" \
  https://artifacts.example.com/generic/main/projects/project-1/data.proprietary
```

**Configuration Files:**
```bash
# Versioned configuration
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@app-config.yaml" \
  https://artifacts.example.com/generic/main/configs/prod/v2/config.yaml
```

## CI/CD Integration

### GitHub Actions Example

```yaml
name: Upload Artifacts

on:
  push:
    tags:
      - 'v*'

jobs:
  upload:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build
        run: make build

      - name: Upload to Generic Storage
        run: |
          curl -X POST \
            -H "Authorization: Bearer ${{ secrets.ARTIFACT_KEEPER_TOKEN }}" \
            -F "file=@dist/output.tar.gz" \
            https://artifacts.example.com/generic/main/releases/${{ github.ref_name }}/output.tar.gz

      - name: Upload ML Model
        run: |
          pip install huggingface_hub
          python -c "
          from huggingface_hub import HfApi
          api = HfApi(endpoint='https://artifacts.example.com/huggingface/main')
          api.upload_folder(folder_path='./models', repo_id='myorg/model')
          "
        env:
          HUGGING_FACE_HUB_TOKEN: ${{ secrets.ARTIFACT_KEEPER_TOKEN }}
```

## Best Practices

### Versioning

- Use semantic versioning for all artifacts
- Include version in file paths for immutability
- Tag releases appropriately

### Metadata

- Always include descriptive metadata
- Add build/commit information
- Include checksums for verification

### Organization

- Use consistent path structures
- Group related artifacts
- Separate environments (dev/staging/prod)

### Security

- Use token authentication
- Restrict access by repository
- Rotate tokens regularly
- Never commit tokens to source control

## Remote & Virtual Repositories

All formats on this page support remote proxy and virtual repository aggregation.

### Common Upstream URLs

| Format | Upstream URL |
|--------|-------------|
| CocoaPods | `https://cdn.cocoapods.org` |
| Pub (Dart/Flutter) | `https://pub.dev` |

### Example: CocoaPods Pull-Through Cache

```bash
curl -X POST http://localhost:8080/api/v1/repositories \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "key": "cocoapods-remote",
    "name": "CocoaPods Remote",
    "format": "cocoapods",
    "repo_type": "remote",
    "upstream_url": "https://cdn.cocoapods.org"
  }'
```

Virtual repositories can combine internal and cached packages for any of these formats. See the [Remote & Virtual Repositories](/docs/advanced/remote-virtual) guide for full setup instructions.
