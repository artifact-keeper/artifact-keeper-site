---
title: What's new in 1.7.3
description: OCI/Docker read authorization, repository-scoped token confinement, migration repo_mappings, and honest backup failure reporting on filesystem storage
---

v1.7.3 closes a cluster of OCI/Docker authorization gaps, including a repository-scoped API token that could read and write every repository its owner could reach, and several private-repository content and metadata leaks through public virtual repositories. Alongside that: PyPI project-name validation, a migration-job repository-renaming option, and backups on filesystem storage correctly reporting failure instead of a false "completed." This release also ships everything that was staged for the retired 1.7.2 build; see [What happened to 1.7.2](/docs/release-notes/v1-7-2/).

For the full commit-level changelog, see [the GitHub release notes](https://github.com/artifact-keeper/artifact-keeper/releases/tag/v1.7.3).

:::caution[Read the upgrade notes before you deploy]
This release changes fail-closed behavior on several authorization and storage paths. A CI pipeline, backup schedule, or alerting rule that depended on the previous (looser) behavior can start failing immediately after upgrade. See **Upgrade notes** below before rolling this out.
:::

## Security

- **OCI/Docker `/v2` reads are authorized against repository visibility, not merely checked for anonymity** ([#3261](https://github.com/artifact-keeper/artifact-keeper/issues/3261)). Previously the only check on the pull path was whether the caller was anonymous, so any authenticated principal could pull any private image by name or digest, and `tags/list` handed a private repository's tag names to the same audience. All five read verbs (`GET`/`HEAD` blob, `GET`/`HEAD` manifest, `GET tags/list`) now run through the same authorization choke point the write path already used. A denial reads as `403` when fine-grained rules govern the repository and `404` (byte-identical to a genuinely missing repository) when none do, so a denial can't be used to probe which private repositories exist. `GET /v2/_catalog` still lists every repository key to any authenticated caller (name enumeration, not content), tracked as [#3269](https://github.com/artifact-keeper/artifact-keeper/issues/3269) for 1.8.0.
- **A repository-scoped API token presented directly to `/v2/` is now confined to its repositories, for reads and writes** ([#3316](https://github.com/artifact-keeper/artifact-keeper/issues/3316)). A token minted with an `allowed_repo_ids` allow-list is the standard containment primitive for CI service accounts and registry mirrors. On the direct-credential path (`docker login`, `-u user:token`, or a raw `Authorization: Bearer <token>`), the scope allow-list was silently discarded, so a token scoped to repository A could read and write every other repository the owning identity held any grant on. Every prior version is affected on any deployment that lets a repository-scoped token reach `/v2/` directly, which is normal Docker/OCI usage.
- **A public Virtual repository no longer serves a private member's bytes to anonymous callers** over Helm, NuGet V2, and Swift downloads ([#3324](https://github.com/artifact-keeper/artifact-keeper/issues/3324)), or leaks a private member's tag names over OCI `tags/list` ([#3320](https://github.com/artifact-keeper/artifact-keeper/issues/3320)). All three now filter through the same member-authorization helper the other proxy formats already use.
- **Quarantine status and SBOM listings are gated on repository visibility, not token scope** ([#3174](https://github.com/artifact-keeper/artifact-keeper/issues/3174)). `GET /api/v1/quarantine/{artifact_id}` and `GET /api/v1/sbom?repository_id=…` previously treated any authenticated caller as in-scope for any repository, disclosing the malware/CVE finding text and dependency inventory of private repositories.
- **Virtual repositories no longer disclose members the caller cannot see** ([#3163](https://github.com/artifact-keeper/artifact-keeper/issues/3163), [#3081](https://github.com/artifact-keeper/artifact-keeper/issues/3081), [#3177](https://github.com/artifact-keeper/artifact-keeper/issues/3177), [#3178](https://github.com/artifact-keeper/artifact-keeper/issues/3178)). Member listing, artifact aggregation, storage-byte totals, and byte resolution all now evaluate the same visibility predicate repository listing uses, in five separate places that previously treated "any grant" or "no rule at all" as sufficient. A follow-on fix ([#3325](https://github.com/artifact-keeper/artifact-keeper/issues/3325)) closes a related gap where a write-only grant on a private member bought read access to it through a virtual repository.
- **SSO logins with an empty subject are rejected instead of collapsing onto one shared account** ([#3204](https://github.com/artifact-keeper/artifact-keeper/issues/3204)). A SAML assertion with an empty or transient `NameID`, or an OIDC token with an empty `sub`, previously provisioned a row keyed on the empty string; every later empty-subject login from the same identity provider silently resolved to that first account.
- **The inline scan-and-block download gate now reaches the virtual-member route of every format** ([#3220](https://github.com/artifact-keeper/artifact-keeper/issues/3220)), closing a bypass where a scan-policy block on a hosted repository was evadable by pulling the same artifact through any virtual repository listing it as a member. The Generic and Terraform byte paths gain the same gate ([#3143](https://github.com/artifact-keeper/artifact-keeper/issues/3143)), and `block_on_fail` now reads the latest scan row per scanner instead of one global newest row, so a crashed scanner can't be masked by a different scanner's clean result ([#3142](https://github.com/artifact-keeper/artifact-keeper/issues/3142)).
- **The PyPI download path is keyed on the normalized project name** ([#3183](https://github.com/artifact-keeper/artifact-keeper/issues/3183)), closing a dependency-confusion evasion where a differently-spelled project name bypassed the ownership gate and curation block while still resolving to the protected package. **PyPI project names are validated against PEP 508** on every route that takes one, including uploads, closing the same normalizer-divergence class structurally rather than patching it again ([#3186](https://github.com/artifact-keeper/artifact-keeper/issues/3186), [#3198](https://github.com/artifact-keeper/artifact-keeper/issues/3198)). **PyPI uploads must carry metadata that agrees with their declared identity.** A wheel or sdist whose embedded metadata names a different project or version than the upload form fields is now rejected ([#3107](https://github.com/artifact-keeper/artifact-keeper/issues/3107)).
- **The fine-grained permissions API is admin-only.** `GET /api/v1/permissions`, `GET /api/v1/permissions/{id}`, and `DELETE /api/v1/permissions/{id}` previously let any authenticated caller page the whole ACL table, and any logged-in non-admin could delete arbitrary permission rows ([#3229](https://github.com/artifact-keeper/artifact-keeper/issues/3229)).
- **Proxy-cache streamed writes are published through a private staging key** instead of the live cache key ([#3152](https://github.com/artifact-keeper/artifact-keeper/issues/3152)), and readers that bypass the cache metadata sidecar are now gated on it ([#3147](https://github.com/artifact-keeper/artifact-keeper/issues/3147)), closing a path where a rejected concurrent write could leave a truncated or zero-byte object as the permanent current version.
- **The bundled scanner CLIs no longer link a vulnerable go-git** (CVE-2026-71556, HIGH). grype moves to v0.117.0 and the scanner-adapter re-pins the in-house trivy build ([#3307](https://github.com/artifact-keeper/artifact-keeper/issues/3307)).

## Added

- **Migration jobs can rename repositories on import** ([#3035](https://github.com/artifact-keeper/artifact-keeper/issues/3035)): `MigrationConfig.repo_mappings` maps a source repository key to the key it lands under (for example `network-team-python` to `network-pypi`); unmapped repositories keep their source name, and a renamed member of a migrated virtual repository keeps its membership. See [From Nexus](/docs/migration/from-nexus/).
- **Curation can verify publisher attestations** ([#2955](https://github.com/artifact-keeper/artifact-keeper/issues/2955)). PyPI and npm curation ingestion now runs on demand, so publisher-trust rules can evaluate packages the proxy has seen. PyPI PEP 740 attestations are verified in process against the DSSE signature, Fulcio chain, SCT, Rekor entry, and inclusion proof. npm attestations are ingested but not verified yet, and fail safe rather than reporting trust, pending an upstream sigstore-rs limitation. See [Package Curation](/docs/security/curation/).
- **Backups can record and tolerate unreadable artifacts.** `BackupManifest` gains `artifacts_unreadable` alongside `artifact_count` so an existing archive can be audited without re-running the backup, and `allow_partial_artifacts` in the backup metadata makes a partial backup an explicit operator choice ([#3170](https://github.com/artifact-keeper/artifact-keeper/issues/3170)). See [Backup & Recovery](/docs/advanced/backup/).
- **Dedicated timeout knobs for the S3 client**: `S3_BULK_TIMEOUT_SECS` (default 1800) and `S3_CONTROL_TIMEOUT_SECS` (default 30), both accepting `0` to disable ([#3180](https://github.com/artifact-keeper/artifact-keeper/issues/3180)). See [Environment Variables](/docs/reference/environment/).

## Fixed

- **`ansible-galaxy collection publish` completes instead of crashing.** The Galaxy v3 publish contract requires a `task` field in the upload response that Artifact Keeper's `202` did not carry; a new import-status route is served alongside it, reporting a synthetic completed import derived from the stored collection rather than a job queue, since publishing is inline ([#3282](https://github.com/artifact-keeper/artifact-keeper/issues/3282)). `ansible-galaxy install` was fixed separately, closing a discovery-route trailing-slash mismatch and an unrecognized `Token` auth scheme ([#3137](https://github.com/artifact-keeper/artifact-keeper/issues/3137)).
- **OpenSCAP `critical` findings are no longer downgraded to `info`** ([#3294](https://github.com/artifact-keeper/artifact-keeper/issues/3294)). The OpenSCAP severity classifier had no `critical` arm, so content reporting a critical rule failure was filed at the least severe bucket, invisible to every gate that reads severity.
- **The dashboard `total_storage_bytes` now includes OCI blob and proxy-cached bytes** ([#3134](https://github.com/artifact-keeper/artifact-keeper/issues/3134), [#3249](https://github.com/artifact-keeper/artifact-keeper/issues/3249)). Previously derived from `artifacts` only, so a Docker repository showed a few kilobytes of manifests while holding gigabytes of layers. `total_storage_bytes` now includes proxy-cached bytes, so `proxy_storage_bytes` is a breakdown of the total rather than a disjoint figure: API consumers that added the two together should stop.
- **`Content-Encoding` is forwarded on proxied downloads** across npm, PyPI, OCI, generic repositories, Cargo's sparse index, Maven, goproxy, RubyGems, Hex, and the buffered scan-gated serve paths ([#2920](https://github.com/artifact-keeper/artifact-keeper/issues/2920), [#3149](https://github.com/artifact-keeper/artifact-keeper/issues/3149), [#3260](https://github.com/artifact-keeper/artifact-keeper/issues/3260), [#3211](https://github.com/artifact-keeper/artifact-keeper/issues/3211), [#3184](https://github.com/artifact-keeper/artifact-keeper/issues/3184), [#3193](https://github.com/artifact-keeper/artifact-keeper/issues/3193)). A content-coded body was being labeled as identity across most proxied formats, so clients wrote compressed bytes to disk and failed checksum verification with no indication why.
- **NuGet's remote-repository cache-repair download resolves the upstream `PackageBaseAddress` and streams**, instead of guessing a URL shape and buffering under an 8 MiB cap ([#2917](https://github.com/artifact-keeper/artifact-keeper/issues/2917)).
- **A `HEAD` request is never answered with a method-scoped presigned redirect.** A presigned URL is signed for one HTTP method, so a `GET`-signed redirect answered to a `HEAD` failed at the object store. Every Gradle build against a repository with `S3_REDIRECT_DOWNLOADS` enabled was affected, since Gradle HEADs before every download ([#3181](https://github.com/artifact-keeper/artifact-keeper/issues/3181), [#3209](https://github.com/artifact-keeper/artifact-keeper/issues/3209)).
- **Digest-addressed proxied OCI manifests stay immutable in the proxy cache**, closing the last classification gap that kept a pull-through Docker cache re-fetching every layer from upstream on every pull ([#3206](https://github.com/artifact-keeper/artifact-keeper/issues/3206)).
- **npm packument responses carry `ETag`, `Cache-Control`, and answer `304`** ([#3052](https://github.com/artifact-keeper/artifact-keeper/issues/3052)), and **objects larger than 5 GiB are copied server-side** on S3 instead of round-tripping through the application ([#3164](https://github.com/artifact-keeper/artifact-keeper/issues/3164)).
- **The Maven repository-delete path spares checksum sidecars and `maven-metadata.xml` rollups that another repository is still serving**, on cloud backends where the flat key space is shared ([#3160](https://github.com/artifact-keeper/artifact-keeper/issues/3160), [#3188](https://github.com/artifact-keeper/artifact-keeper/issues/3188), [#3156](https://github.com/artifact-keeper/artifact-keeper/issues/3156), [#3197](https://github.com/artifact-keeper/artifact-keeper/issues/3197)).
- **The startup warning claiming permission enforcement is inactive is removed.** It was stale text left over from before enforcement landed, and it misled operators about their security posture ([#3185](https://github.com/artifact-keeper/artifact-keeper/issues/3185)).

## Performance

- Health probes for LDAP, OpenSearch, and Trivy are TTL-cached, collapsing an unbounded per-request fan-out on `/health` to one probe per dependency per window ([#3127](https://github.com/artifact-keeper/artifact-keeper/issues/3127)). Previously an anonymous request storm against `/health` became a directory-connection storm against LDAP.
- npm packument responses revalidate with `304` instead of re-sending tens of megabytes per metadata request ([#3052](https://github.com/artifact-keeper/artifact-keeper/issues/3052)).

## Upgrade notes

- **There is no 1.7.2.** If you are upgrading from 1.7.1, go straight to 1.7.3. See [What happened to 1.7.2](/docs/release-notes/v1-7-2/).
- **Migration 193 blocks OCI writes while it builds an index, and the backend does not answer health probes during that window.** `docker pull` keeps working while `docker push` hangs for the duration: that asymmetry is the diagnostic signature. Size `oci_blobs` before upgrading (`SELECT count(*) FROM oci_blobs`), and on Kubernetes raise your startup/liveness probe thresholds before deploying, or build the index out of band first with `CREATE INDEX CONCURRENTLY idx_oci_blobs_storage_key ON oci_blobs (storage_key)` so the migration's `CREATE INDEX IF NOT EXISTS` becomes a no-op.
- **Rolling back to 1.7.1 requires `SKIP_MIGRATIONS=true`.** The 1.7.3 schema is forward-compatible with a 1.7.1 binary, but sqlx's migration ledger validation makes a 1.7.1 binary refuse to start against a 1.7.3 database unless migrations are skipped. All three new migrations are additive; there is no data to lose in a rollback.
- **Authenticated callers now need a grant to pull private OCI/Docker repositories.** This is a fail-closed change (see Security above): a CI service account holding only an API token and no role assignment or fine-grained rule will start being denied on private repositories it previously could read. Audit and grant access before upgrading.
- **Backups on filesystem storage start reporting `failed` on any instance holding artifacts.** This is not a regression: filesystem-backed backup archives have never contained artifact bytes (a pre-existing gap tracked separately), and this release is the first to report that honestly instead of claiming `completed` with `artifact_count=0`. Object-storage deployments (S3/GCS/Azure) are unaffected. Keep an independent filesystem-level snapshot of your storage path: the archive is a metadata backup.
- **PyPI project names that were never valid become permanently unreachable.** Malformed names were previously coerced rather than rejected, and some were stored; the new PEP 508 validation makes them unreachable at any URL with no automatic repair. See the SQL query in the GitHub release notes to inventory affected artifacts before upgrading.
- **Storage alerts will fire on upgrade day.** `total_storage_bytes` now includes OCI blob and proxy-cached bytes it previously omitted, so a Docker-heavy registry's reported total steps up in one day. This is a display-only correction; quota admission was already reading the correct per-repository figures and is unchanged.
- **`helm push oci://` into a classic Helm repository now returns `400`**, and charts previously pushed that way disappear from `index.yaml` generation: that index was never valid. Re-publish affected charts to a `helm_oci` repository or as classic charts.

## Upgrade path

1. **Size `oci_blobs`** and, on a large registry, build its new index out of band before deploying (see Upgrade notes above).
2. **Pull the new images**:
   ```bash
   docker pull ghcr.io/artifact-keeper/artifact-keeper-backend:1.7.3
   docker pull ghcr.io/artifact-keeper/artifact-keeper-web:1.7.3
   ```
3. **Audit OCI/Docker grants** for any service account or CI identity that pulls private repositories directly (see the query in the GitHub release notes) and grant access before rolling out.
4. **Raise Kubernetes startup/liveness thresholds** to cover the migration window, or skip it entirely by pre-building the index.
5. **Review your PyPI project namespace** for names that predate PEP 508 validation, if you allow arbitrary uploads.
6. **Helm / Docker Compose**: bump to the v1.7.3-compatible chart or compose file and apply.
7. **Silence or re-baseline storage-growth alerts** for 48 hours around the cut.

The web UI, CLI, and native clients work unchanged against a 1.7.3 backend. SDKs published to npm, Maven, PyPI, crates.io, and SPM are tagged `1.7.3`.
