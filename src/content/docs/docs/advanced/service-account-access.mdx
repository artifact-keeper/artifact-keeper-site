---
title: "Give a service account access to a repository"
description: "Token scope, account grants, group membership, and which credential shape each route accepts"
---

A service account reaches a repository only when two separate checks both pass. Most failed setups are missing one of them, or send the token in a shape the route does not accept.

## The Two Checks

**Token scope is the ceiling.** You set it when you mint the token. "Repository access" on the token form restricts which repositories the token may reach. Leave it empty and the token is unrestricted. A token can never grant more than the account itself holds.

**Account grants are the entitlement.** The service account needs a permission that carries the `read` action on the repository. That can be:

- a direct rule: principal = the service account, target = the repository, or
- a rule on a group the service account is a member of: principal = the group, target = the repository.

Both checks are needed. A token scoped to the repository does nothing if the account has no grant. A grant does nothing if the token's scope excludes the repository.

Admin accounts bypass the grant check. An API token owned by an admin is only admin when the token itself was minted with the `admin` scope. This is deliberate (GHSA-vvc3-h39c-mrq5): a narrow token minted by an admin stays narrow.

## Membership Is Not a Group-Target Permission

Membership is managed on the Groups page: Administration, Groups, pick the group, Members, add the account. Membership is what carries the group's repository rules to the account.

A permission rule whose target is a group is a different thing. A rule such as principal = service account, target = group, action = `read` controls who can view or manage the group itself. It does not make the principal a member, and it does not confer the group's repository access.

:::caution
This is the single most common misconfiguration (#4593). To give a service account a group's repository access, add it as a member on the Groups page. Do not create a permission rule that targets the group.
:::

## A 404 Means Not Entitled

A private repository the caller is not entitled to read answers 404, not 403, so the repository's existence is not leaked. A 404 for a repository you know exists usually means one of:

- the account has no `read` grant on the repository,
- the token's scope excludes the repository, or
- the credential was never sent (see below).

## Which Credential Shape Works Where

**Format routes** (`/maven/{repo}/...`, `/npm/{repo}/...`, `/pypi/...`, `/cargo/...`, `/v2/...` and the other package-manager endpoints) accept HTTP Basic with the API token in the password field. The username can be anything. These routes also answer a request with no credential with a 401 challenge, so Maven, pip, npm, wget and curl work with their normal credential settings.

```bash
curl -u anyuser:<token> https://registry.example.com/maven/<repo>/<path>
```

**The management API** (`/api/v1/*`, including `GET /api/v1/repositories/{key}/download/{path}`) takes the token as `Authorization: Bearer <token>` or as an `X-API-Key` header. An API token in the Basic password field is refused here.

```bash
wget --header="Authorization: Bearer <token>" \
  https://registry.example.com/api/v1/repositories/<key>/download/<path>
```

In 1.11.0 the download route answers an anonymous request on a private repository with 404 and no 401 challenge. Clients that only send credentials after a challenge (wget with `--user` and `--password`, curl without pre-auth, Maven) never send the token, so they get that 404. Send the header up front, as in the wget example.

:::note
From 1.11.1 (#4654) the download route will challenge with 401 and accept the token as the Basic password, like the format routes.
:::

To confirm which principal the server sees, call `/api/v1/auth/me` with the bearer header:

```bash
curl -H "Authorization: Bearer <token>" https://registry.example.com/api/v1/auth/me
```

## Troubleshooting

Work through these in order.

1. Does `GET /api/v1/auth/me` with the token return the service account? If not, the token is wrong, expired, or sent in a shape the route does not accept.
2. Is the repository in the token's scope? Check "Repository access" on the token. Empty means unrestricted.
3. Does the account hold `read` on the repository, either directly or through a group it is a member of? A rule that targets the group does not count.
4. Are you sending the credential in a shape that route accepts? Bearer header on `/api/v1/*`; Basic with the token as the password on the format routes.
