Artifact Keeper supports cryptographic signing and verification of artifacts to ensure authenticity, integrity, and establish content trust throughout your software supply chain.

## Overview

Artifact signing provides:

- **Authenticity**: Verify artifacts come from trusted sources
- **Integrity**: Ensure artifacts haven't been tampered with
- **Non-repudiation**: Cryptographic proof of origin
- **Compliance**: Meet regulatory requirements for software provenance

## Supported Signing Methods

### Container Images

- **Cosign**: Sigstore's container signing tool
- **Docker Content Trust**: Notary-based signing
- **OCI Signatures**: OCI artifact manifest signatures

### Packages

- **GPG Signatures**: Universal PGP/GPG signing
- **Language-Specific**:
  - RPM: GPG signing
  - Debian/APK: GPG signing
  - Maven: PGP signatures
  - npm: Package signing

## Cosign Integration

Cosign is the recommended method for signing container images.

### Installation

```bash
# Install cosign
brew install cosign

# Or download from GitHub releases
wget https://github.com/sigstore/cosign/releases/latest/download/cosign-linux-amd64
chmod +x cosign-linux-amd64
sudo mv cosign-linux-amd64 /usr/local/bin/cosign
```

### Generate Signing Keys

```bash
# Generate key pair
cosign generate-key-pair

# Enter password for private key
# Creates cosign.key and cosign.pub
```

### Sign Container Image

```bash
# Push image to registry
docker push localhost:8080/my-app:1.0.0

# Sign the image
cosign sign --key cosign.key localhost:8080/my-app:1.0.0
```

With keyless signing (Sigstore):

```bash
# Sign using OIDC identity
cosign sign localhost:8080/my-app:1.0.0
```

### Verify Signature

```bash
# Verify with public key
cosign verify --key cosign.pub localhost:8080/my-app:1.0.0

# Verify keyless signature
cosign verify \
  --certificate-identity=user@example.com \
  --certificate-oidc-issuer=https://accounts.google.com \
  localhost:8080/my-app:1.0.0
```

### Verifying with Podman, Skopeo, bootc and Anaconda

`cosign verify` and the containers/image library (used by Podman, Skopeo, CRI-O, bootc and Anaconda's `ostreecontainer`) look for signatures in different places:

| Client | Reads |
|--------|-------|
| `cosign verify` (cosign 3 defaults) | Sigstore bundle attached through the OCI referrers API, or the legacy `.sig` tag |
| Podman, Skopeo, CRI-O, bootc, Anaconda (containers/image) | Only the legacy sigstore attachment: a `sha256-<digest>.sig` tag next to the image |

With its defaults, cosign 3 writes the new Sigstore bundle format and attaches it with the referrers API (and expects Rekor/TUF). Artifact Keeper stores and serves that correctly, but containers/image cannot see it: `cosign verify` succeeds while `podman pull` under a `sigstoreSigned` policy fails with `A signature was required, but no signature exists`. To produce signatures both kinds of client can verify, use one of the following.

**cosign, legacy attachment format:**

```bash
# cosign does not read Podman's auth file: log in with cosign
# (or point DOCKER_CONFIG at a directory containing config.json)
cosign login registry.example.com:30080 -u username -p "$TOKEN"

cosign sign --yes --key cosign.key \
  --tlog-upload=false --new-bundle-format=false --use-signing-config=false \
  registry.example.com:30080/oci-bootc/rocky-edge@sha256:<digest>
```

Add `--allow-http-registry --allow-insecure-registry` when the registry is served over plain HTTP (for example port 30080 of the stock compose stack). cosign prints a deprecation warning for `--new-bundle-format`; pin the cosign version you sign with so that a later release does not silently change the format.

**Podman, signing while pushing:**

```bash
podman push --sign-by-sigstore-private-key cosign.key \
  registry.example.com:30080/oci-bootc/rocky-edge:10
```

Podman writes the signature as a sigstore attachment only when the `registries.d` entry below is present on the pushing host as well.

#### Client configuration

containers/image only reads (and writes) sigstore attachments for registries that enable them in `registries.d`, for example `/etc/containers/registries.d/artifact-keeper.yaml`:

```yaml
docker:
  registry.example.com:30080/oci-bootc:
    use-sigstore-attachments: true
```

Then require a signature in `/etc/containers/policy.json`:

```json
{
  "default": [{ "type": "insecureAcceptAnything" }],
  "transports": {
    "docker": {
      "registry.example.com:30080/oci-bootc/rocky-edge": [
        {
          "type": "sigstoreSigned",
          "keyPath": "/etc/pki/containers/edge-cosign.pub",
          "signedIdentity": { "type": "matchRepository" }
        }
      ]
    }
  }
}
```

Podman, Skopeo, bootc and Anaconda read the same `policy.json` and `registries.d` on the host.

#### `signedIdentity` and registry host names

A signature records the image name the signer used. cosign records the repository without a tag (for example `"docker-reference": "localhost:30080/oci-bootc/rocky-edge"`), so:

- The default `signedIdentity` (`matchRepoDigestOrExact`) rejects a pull by tag. Use `matchRepository` when every client reaches the registry under the same name as the signer.
- When clients reach the registry under a different host name than the signer used (for example the signer pushed to `localhost:30080` and nodes pull from `10.0.2.2:30080` or `registry.internal:30080`), the names differ and verification fails. Pin the signed name with `exactRepository`:

```json
"10.0.2.2:30080/oci-bootc/rocky-edge": [
  {
    "type": "sigstoreSigned",
    "keyPath": "/etc/pki/containers/edge-cosign.pub",
    "signedIdentity": {
      "type": "exactRepository",
      "dockerRepository": "localhost:30080/oci-bootc/rocky-edge"
    }
  }
]
```

To map a whole namespace, use `remapIdentity` (`"prefix": "10.0.2.2:30080/oci-bootc", "signedPrefix": "localhost:30080/oci-bootc"`).

Signatures are attached to the manifest digest, so promoting an image by re-tagging it within the same repository (for example `skopeo copy docker://.../rocky-edge:10.2-4 docker://.../rocky-edge:10`) needs no re-signing.

## GPG Signing

### Generate GPG Key

```bash
# Generate new GPG key
gpg --full-generate-key

# List keys
gpg --list-keys

# Export public key
gpg --armor --export your-email@example.com > public.key

# Export private key (keep secure!)
gpg --armor --export-secret-key your-email@example.com > private.key
```

### Sign Files with GPG

```bash
# Sign a file
gpg --detach-sign --armor artifact.tar.gz
# Creates artifact.tar.gz.asc

# Sign and encrypt
gpg --sign --armor artifact.tar.gz
```

### Verify GPG Signature

```bash
# Import public key
gpg --import public.key

# Verify signature
gpg --verify artifact.tar.gz.asc artifact.tar.gz
```

## Linux Package Signing

### RPM Signing

Configure RPM signing:

```bash
# Create GPG key for RPM signing
gpg --full-generate-key

# Import key to RPM database
rpm --import public.key

# Configure ~/.rpmmacros
cat > ~/.rpmmacros <<EOF
%_signature gpg
%_gpg_name your-email@example.com
EOF
```

Sign RPM package:

```bash
# Sign package
rpm --addsign package.rpm

# Verify signature
rpm --checksig package.rpm
```

### Debian Package Signing

Sign Debian packages:

```bash
# Sign package
dpkg-sig --sign builder package.deb

# Verify signature
dpkg-sig --verify package.deb
```

Create signed repository:

```bash
# Create Release file
apt-ftparchive release . > Release

# Sign Release file
gpg --clearsign -o InRelease Release
gpg -abs -o Release.gpg Release

# Export public key for users
gpg --armor --export your-email@example.com > repository.key
```

### Alpine Package Signing

Sign APK packages:

```bash
# Generate signing key
openssl genrsa -out signing.key 2048
openssl rsa -in signing.key -pubout -out signing.pub

# Sign package
abuild-sign package.apk
```

## Signing Key Management

Artifact Keeper generates and stores repository signing keys server-side and uses them to sign repository metadata on the fly. All signing endpoints require an administrator.

### API Endpoints

```
GET    /api/v1/signing/keys                          # List keys (optional ?repository_id=<uuid>)
POST   /api/v1/signing/keys                          # Generate a new key
GET    /api/v1/signing/keys/{key_id}                 # Get key details
DELETE /api/v1/signing/keys/{key_id}                 # Delete key
POST   /api/v1/signing/keys/{key_id}/revoke          # Revoke key
POST   /api/v1/signing/keys/{key_id}/rotate          # Rotate key
GET    /api/v1/signing/keys/{key_id}/public          # Public key
GET    /api/v1/signing/repositories/{repo_id}/config # Repository signing config
POST   /api/v1/signing/repositories/{repo_id}/config # Update repository signing config
GET    /api/v1/signing/repositories/{repo_id}/public-key # Repository's public key
POST   /api/v1/signing/artifacts/{artifact_id}/sign  # Sign one artifact (promotion attestation)
```

There is no signature-verification endpoint and no key upload: `POST /api/v1/signing/keys` generates the key pair on the server. `{repo_id}` is the repository **UUID** (the `id` field of `GET /api/v1/repositories/{key}`), not its key.

### Generate a Key

```bash
POST /api/v1/signing/keys
Content-Type: application/json

{
  "name": "rpm-stable repodata",
  "key_type": "gpg",
  "algorithm": "rsa4096",
  "repository_id": "<repository uuid>",
  "uid_name": "Artifact Keeper rpm-stable",
  "uid_email": "rpm-stable@example.com"
}
```

`key_type` is one of `gpg`, `rsa` or `ed25519` (default `rsa`); `algorithm` defaults to `rsa4096`. RPM and Debian metadata signatures are OpenPGP signatures and need a `gpg` key; Alpine `APKINDEX` signatures use an `rsa` key. The response contains the key's `id`, `fingerprint`, `key_id` and `public_key_pem`. `GET /api/v1/signing/keys` returns `{"keys": [...], "total": n}`.

### Enable Metadata Signing for a Repository

```bash
POST /api/v1/signing/repositories/<repository uuid>/config
Content-Type: application/json

{
  "signing_key_id": "<key id>",
  "sign_metadata": true
}
```

The config also accepts `sign_packages` and `require_signatures` flags.

Once metadata signing is on, the repository serves signed metadata:

| Format | Signature | Public key |
|--------|-----------|------------|
| RPM | `/rpm/<key>/repodata/repomd.xml.asc` | `/rpm/<key>/repodata/repomd.xml.key` |
| Debian | `/debian/<key>/dists/<dist>/InRelease`, `Release.gpg` | `/debian/<key>/gpg-key.asc` |
| Alpine | signed `APKINDEX.tar.gz` | `/alpine/<key>/<branch>/keys/artifact-keeper.rsa.pub` |

For RPM, `dnf` verifies the metadata signature with `repo_gpgcheck=1`:

```ini
[artifact-keeper]
name=Artifact Keeper Repository
baseurl=https://registry.example.com/rpm/stable
enabled=1
repo_gpgcheck=1
gpgkey=https://registry.example.com/rpm/stable/repodata/repomd.xml.key
```

Remote (proxy) RPM repositories pass the upstream `repomd.xml.asc` through unchanged; configure clients with the upstream's key for those.

### Signature Expiry and Mirrors

OpenPGP repository-metadata signatures (Debian `InRelease` / `Release.gpg`, RPM `repomd.xml.asc`) carry an expiration time set by `SIGNATURE_EXPIRY_SECONDS`:

- Default `604800` (7 days). Values are clamped to the range `7200` to `31536000`; `0` disables the expiry.
- The registry re-signs metadata on request, so clients fetching directly always receive a signature well inside its validity window.
- A downstream mirror or air-gapped export that copies the signature once fails verification after the window has passed (`apt` itself does not enforce signature expiry, but `gpgv`, `debmirror` and other mirror tooling do). Refresh mirrors more often than the window, or raise `SIGNATURE_EXPIRY_SECONDS`.

See the [environment variable reference](/docs/reference/environment/).

## Promotion Signature Requirements

Promotion rules can require a signature (`require_signature`). An artifact satisfies it only after an administrator signs its content with the repository's active key:

```bash
POST /api/v1/signing/artifacts/{artifact_id}/sign
```

Proxy-cached artifacts from remote repositories cannot be signed this way and therefore do not pass a `require_signature` gate.

## Integration with CI/CD

### GitHub Actions with Cosign

```yaml
name: Build, Sign, and Push
on: [push]

jobs:
  build-and-sign:
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      packages: write
      contents: read

    steps:
      - uses: actions/checkout@v4

      - name: Install Cosign
        uses: sigstore/cosign-installer@v3

      - name: Login to registry
        uses: docker/login-action@v3
        with:
          registry: registry.example.com
          username: ${{ secrets.REGISTRY_USERNAME }}
          password: ${{ secrets.REGISTRY_PASSWORD }}

      - name: Build image
        run: |
          docker build -t registry.example.com/my-app:${{ github.sha }} .
          docker push registry.example.com/my-app:${{ github.sha }}

      - name: Sign image (keyless)
        run: |
          cosign sign --yes registry.example.com/my-app:${{ github.sha }}
```

### With Private Keys

```yaml
- name: Sign image (with key)
  env:
    COSIGN_KEY: ${{ secrets.COSIGN_PRIVATE_KEY }}
    COSIGN_PASSWORD: ${{ secrets.COSIGN_PASSWORD }}
  run: |
    echo "$COSIGN_KEY" > cosign.key
    cosign sign --key cosign.key registry.example.com/my-app:${{ github.sha }}
```

### Maven PGP Signing

```yaml
- name: Sign and deploy Maven artifact
  env:
    GPG_PRIVATE_KEY: ${{ secrets.GPG_PRIVATE_KEY }}
    GPG_PASSPHRASE: ${{ secrets.GPG_PASSPHRASE }}
  run: |
    echo "$GPG_PRIVATE_KEY" | gpg --import
    mvn clean deploy -Pgpg
```

Configuration in `pom.xml`:

```xml
<profiles>
  <profile>
    <id>gpg</id>
    <build>
      <plugins>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-gpg-plugin</artifactId>
          <version>3.1.0</version>
          <executions>
            <execution>
              <id>sign-artifacts</id>
              <phase>verify</phase>
              <goals>
                <goal>sign</goal>
              </goals>
            </execution>
          </executions>
        </plugin>
      </plugins>
    </build>
  </profile>
</profiles>
```

## Transparency Logs

### Sigstore Rekor

Artifact Keeper can integrate with Rekor for transparency logging:

```yaml
# config/rekor.yaml
rekor:
  enabled: true
  url: "https://rekor.sigstore.dev"
  log_signatures: true
  verify_inclusion: true
```

Signatures are logged to Rekor:

```bash
# Sign and log
cosign sign --rekor-url https://rekor.sigstore.dev \
  localhost:8080/my-app:1.0.0

# Verify with transparency log
cosign verify --rekor-url https://rekor.sigstore.dev \
  localhost:8080/my-app:1.0.0
```

### Search Transparency Logs

```bash
# Search for signatures
rekor-cli search --artifact localhost:8080/my-app:1.0.0

# Get log entry
rekor-cli get --uuid <uuid>
```

## Signature Storage

### Signature Artifacts

Signatures can be stored as:

1. **Attached Signatures**: Stored alongside artifact
2. **OCI Artifacts**: Signatures as OCI artifacts (recommended)
3. **Separate Files**: .sig or .asc files

### OCI Signature Format

Cosign stores signatures as OCI artifacts:

```
registry.example.com/my-app:1.0.0
registry.example.com/my-app:sha256-<digest>.sig
```

View signatures:

```bash
# List signatures
cosign tree localhost:8080/my-app:1.0.0
```

## Attestations

Sign and verify attestations about artifacts:

### Create Attestation

```bash
# Create SLSA provenance attestation
cosign attest --key cosign.key \
  --predicate provenance.json \
  --type slsaprovenance \
  localhost:8080/my-app:1.0.0
```

### Verify Attestation

```bash
# Verify attestation
cosign verify-attestation --key cosign.pub \
  --type slsaprovenance \
  localhost:8080/my-app:1.0.0
```

### Attestation Types

- **SLSA Provenance**: Build provenance information
- **SBOM**: Software Bill of Materials
- **Vulnerability Scan**: Scan results attestation
- **Custom**: Application-specific attestations

## Best Practices

### Key Management

- Use hardware security modules (HSM) for production keys
- Rotate keys regularly
- Use separate keys for different environments
- Never commit private keys to version control
- Use key management services (AWS KMS, Google KMS, Azure Key Vault)

### Signing Workflow

1. Build artifact in secure environment
2. Run security scans
3. Generate attestations (SBOM, provenance)
4. Sign artifact and attestations
5. Upload to registry
6. Log to transparency log
7. Verify before deployment

### Verification

- Always verify signatures before deployment
- Use keyless signing when possible
- Require attestations for production artifacts
- Integrate verification into CI/CD gates
- Monitor signature verification failures

### Compliance

- Document signing procedures
- Maintain key inventory
- Audit signature operations
- Implement key rotation policies
- Meet regulatory requirements (FIPS, Common Criteria)

## Troubleshooting

### Signature Verification Failures

Check signature exists:

```bash
cosign tree localhost:8080/my-app:1.0.0
```

Verify with correct key:

```bash
cosign verify --key cosign.pub localhost:8080/my-app:1.0.0
```

Check certificate details:

```bash
cosign verify localhost:8080/my-app:1.0.0 --insecure-ignore-tlog
```

### Key Issues

Test GPG key:

```bash
gpg --list-keys
gpg --test-sign
```

Verify key permissions:

```bash
chmod 600 cosign.key
```

### OIDC Issues

For keyless signing, verify OIDC token:

```bash
cosign sign --verbose localhost:8080/my-app:1.0.0
```
